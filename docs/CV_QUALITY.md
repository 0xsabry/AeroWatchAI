# AeroWatch AI — Computer Vision Quality Report (Phase 2)

All numbers below were **measured** with `evaluation/model_benchmark.py`
(COCO-style AP: greedy confidence-ordered matching, 101-point
interpolation) on the project's own annotated test artifacts, in a
CPU-only environment (no GPU). Reproduce with:

```
python evaluation/model_benchmark.py weights/aerowatch_v7_balanced.pt
python evaluation/model_benchmark.py weights/aerowatch_v7_balanced.pt \
    --nms-iou 0.45 --canonical-dedup        # the improved configuration
```

Raw JSON for every run cited here is produced under
`evaluation/results/` (git-ignored, regenerated by the commands above).

## 1. Dataset

`tests/artifacts/`: 30 annotated images + 5 negative images, 38 ground
truth boxes — Drone 16, Aircraft 16, Bird 4, Balloon 2. Sources are
documented per-image in `tests/artifacts/manifest.json` (Rigoleto
drone-detection, Open Images, matisdsp drone-bird, a balloon set, and
authentic flight captures; CC-BY where licensed).

**Limitations, stated plainly:**

- **Small and imbalanced.** Balloon (n=2) and Bird (n=4) per-class
  metrics are indicative only. Most images are clear-daylight; the
  manifest tags only 3 "small_object", 2 "distant", 1 "motion_blur",
  1 "cluttered_background" — adverse-condition performance is
  essentially unmeasured by this set.
- **Leakage cannot be excluded.** The training data is *not in this
  repository* (no dataset directory, no data YAML; training scripts
  reference external paths). Some artifact filenames come from source
  datasets' own *train* splits (e.g. `rigo_rigoleto_train0022.jpg`), so
  whether the checkpoint trained on these very images is unknowable
  from here. Treat all scores as an upper bound until a verified
  held-out set exists.
- One airliner image (`air_airliner_07f2...jpg`) appears to contain a
  second, unannotated aircraft; two of the model's "false positives"
  there may be annotation gaps rather than model errors.

## 2. Baseline reproduced (production checkpoint, app defaults)

`aerowatch_v7_balanced.pt` (= `best.pt`, identical SHA-256), imgsz 640,
NMS IoU 0.7, operating point conf 0.25:

| Metric | Value |
|---|---|
| **mAP50** | **0.968** |
| **mAP50-95** | **0.689** |
| Precision / Recall / F1 @0.25 | 0.805 / 0.868 / 0.835 |
| FP / FN @0.25 | 8 / 5 |
| Calibration ECE | 0.135 |
| CPU latency (this sandbox) | ~98 ms/img warm, load ~3.8 s |

Per class @0.25: Drone AP50 0.969 (P 0.933, R 0.875) · Aircraft AP50
0.953 (P 0.737, R 0.875) · Bird AP50 0.950 (P 1.000, R 0.750, n=4) ·
Balloon AP50 1.000 (P 0.500, R 1.000, n=2).

Note on the repo's older figures: `reports/validation/summary.json`
reported "map50_estimated 0.699" from a single-IoU proxy. Measured
properly, mAP50 is 0.968 and mAP50-95 is 0.689 — the old "estimate" was
in fact close to the mAP50-95. The README's "84.6% mAP" matches
neither metric. The old summary's P/R (0.805/0.868) reproduce exactly
under this harness, which cross-validates it.

| Checkpoint | mAP50 | mAP50-95 | F1 @0.25 | Notes |

| v5_pro | 0.476 | 0.389 | 0.346 | Aircraft AP50 only 0.155 |
| YOLO11n (COCO, downloaded) | 0.390 | 0.332 | 0.507 | no Drone/Balloon classes exist |

| YOLOv8n (COCO, downloaded) | 0.337 | 0.286 | 0.406 | no Drone/Balloon classes exist |

**Conclusion:** v7's advantage is task fine-tuning, not architecture.
No off-the-shelf checkpoint comes close, and COCO models structurally
cannot detect the two most important classes (Drone, Balloon).
**The production checkpoint is not replaced.** A future architecture
change only makes sense as a *retraining* project on a real dataset
(see §7). All listed architectures are Ultralytics YOLO — AGPL-3.0 for
open-source use; commercial deployment needs their enterprise licence.
That constraint applies equally to the current checkpoint.

## 4. Error analysis (v7, operating point)

- **Zero cross-class confusions** at IoU 0.5: no Drone↔Bird, no
  Drone↔Balloon mix-ups among matched detections. Errors are
  detection/localisation failures, not classification swaps.
- **False positives (8 @0.25)** concentrate on airliner images: extra
  partial-aircraft boxes, and — found by this phase — **canonical
  duplicates**: the checkpoint declares *both* `aircraft` and
  `military_jet`, which normalise to the same canonical "Aircraft".
  YOLO NMS is per-raw-class, so one physical airliner survived NMS
  twice (boxes at IoU ≈ 0.98, conf 0.43 + 0.33) and was reported as
  two aircraft. Two Balloon FPs are second boxes on single-balloon
  images. One Drone FP (0.43) sits on a drone-vs-bird dataset image.
- **False negatives (5 @0.25):** a tiny drone (0.12% of frame area —
  the small-object limit), a drone filling 83% of the frame (unusual
  scale), one large bird, two medium aircraft. Even at conf 0.05,
  recall caps at 0.947: two GT are effectively invisible to this
  model at any threshold.
- **Size strata recall @0.25:** small (<1% area) 0.50 (n=2), medium
  0.913 (n=23), large 0.846 (n=13).
- **Calibration:** confidence is meaningful only at the top end.
  Empirical precision by confidence bin: 0.3–0.4 → 0.00, 0.4–0.5 →
  0.33, 0.5–0.6 → 1.00, 0.6–0.7 → 0.60, 0.7–0.8 → 1.00, 0.8–0.9 →
  0.94, 0.9–1.0 → 1.00. Predictions below ~0.50 should be presented
  as *uncertain* — the app now defaults its Uncertain Floor to 0.50.

## 5. Experiments

| Experiment | Result (same dataset/method) | Decision |
|---|---|---|
| NMS IoU 0.7 → 0.6 → 0.45 | F1 @0.25: 0.835 → 0.868 → 0.880; FP 8 → 5 → 4, recall unchanged 0.868; mAP50-95 0.689 → 0.665 → 0.651 | **Adopt 0.45** (operating-point gain outweighs the small mAP50-95 cost for a thresholded display app; both numbers reported, not hidden) |
| Canonical dedup (new) | duplicates 2 → 0; with NMS 0.7: F1 0.835 → 0.857, FP 8 → 6, recall and mAP unchanged | **Adopted** in `filter_airspace_detections` |
| NMS 0.45 + dedup combined | **P 0.943 / R 0.868 / F1 0.904, FP 2, FN 5 @ conf 0.25** | **Adopted as the app configuration** |
| imgsz 640 → 960 → 1280 | F1 0.835 → 0.821 → 0.630; FP 8 → 8 → 25; CPU latency ×1.6 / ×3.4 | **Keep 640.** The app's image tab was using 1280 — the single worst measured setting — and is fixed to 640 |
| Threshold sweep | F1 peaks at conf 0.45–0.50 (0.877) but costs recall (0.868 → 0.842) | Not adopted as default: with NMS 0.45 + dedup, conf 0.25 already reaches F1 0.904 *without* hiding detections. The sweep is in every benchmark JSON for operators to choose knowingly |
| ONNX export + ORT CPU | parity: 35/37 torch detections matched at IoU ≥ 0.9 (mean IoU 0.977, max conf Δ 0.082 — two borderline boxes flip); CPU latency ~147 ms vs ~235 ms in the same run (~1.6× faster); FP32 ONNX is 9.8 MB vs 5.4 MB .pt | **Recommended, not yet integrated:** ORT removes the pickle code-execution surface (Phase 1's top remaining risk) and is faster on CPU, but borderline-detection drift means it ships only behind the same benchmark gate, as its own change |

## 6. What changed in code

- `ai_safety.dedupe_canonical()` + integration in
  `ModelManager.filter_airspace_detections` (so the app, video
  pipeline and CLI all inherit it), with tests.
- NMS IoU 0.45 at all app inference sites (`app.py` image + live,
  `video_processor.py`, `predict_image.py --nms-iou`).
- `app.py` still-image inference 1280 → 640.
- Uncertain Floor default 0.40 → 0.50 (`app.py` slider,
  `predict_image.py --uncertain`) — calibration-backed.
- `predict_image.py` output now shows, per detection: confidence,
  certainty band, and safety-posture status, plus an explicit note
  that detections are unverified predictions, not facts or proof of
  intent.
- `evaluation/model_benchmark.py`: the reproducible benchmark used
  for every number above (mAP50, mAP50-95, per-class P/R, confusion,
  calibration/ECE, size strata, duplicate count, PR sweep, latency).

No safety control from Phase 1 was removed or weakened; the
`ai_safety` contract still gates every detection before display.

## 7. Remaining weaknesses & next steps

1. **The evaluation set is too small to certify anything.** Priority
   one is a larger, provenance-clean held-out set (hundreds of images
   per class, adverse conditions, verified disjoint from training),
   before any further model claims are made.
2. **Training provenance is unknown** — no dataset, data YAML, or
   training config in the repo. Retraining (the only route past the
   current recall ceiling and the two invisible GT) is impossible to
   reproduce until the training set is recovered or rebuilt.
3. **Small/distant objects** remain the weakest stratum (recall 0.50,
   n=2 — needs more data before conclusions). Slicing/tiling (SAHI-
   style) is a candidate experiment once data exists; raising imgsz
   was tested and *hurts* this checkpoint.
4. **RTX 3050 numbers were not measured in this phase** — this
   environment has no GPU. The repo's own 2026-10-12 artifacts
   (~11.8–15.8 ms FP16) remain the only GPU evidence; re-run
   `evaluation/model_benchmark.py` on the target machine to replace
   them (it reports latency on whatever device runs it, and the same
   JSON schema makes results comparable).
5. **ONNX Runtime backend** (§5) as a scoped follow-up: parity-gated,
   removes pickle loading, ~1.6× CPU speedup measured.
6. **Temporal consistency for video** was not implemented: the
   artifact videos are already handled by the tracker in
   `evaluate_videos.py`, and this phase found no measured video-FP
   problem to justify new filtering. Revisit with real video
   error data rather than speculation.
